gateway ​

gateway dispatches requests to middleware chains with the matching rules of the Kubernetes Gateway API HTTPRoute. The Kubernetes provider generates it, but it can also be used directly.

yaml
server:
  http:
    middlewares:
      api_v1:
        service:
          loadbalancer:
            servers:
              - url: http://v1:3000
      api_v2:
        service:
          loadbalancer:
            servers:
              - url: http://v2:3000
      routes:
        gateway:
          rules:
            - matches:
                - path: { type: prefix, value: /api }
                  headers:
                    - { name: X-Canary, value: "true" }
              middlewares: [api_v2]
            - matches:
                - path: { type: prefix, value: /api }
              filters:
                - request_headers:
                    set: { X-Gateway: turna }
              backends:
                - { weight: 90, middlewares: [api_v1] }
                - { weight: 10, middlewares: [api_v2] }
            - matches:
                - path: { type: exact, value: /old }
              filters:
                - redirect: { path: { replace_full_path: /new }, status_code: 301 }
    routers:
      main:
        path: [/*]
        middlewares: [routes]

Matching ​

A rule matches when any of its matches match; an empty list matches every request. Within a match, all conditions must hold.

FieldDescription
path.typeprefix (default, matches whole path segments: /api matches /api/x but not /apix), exact or regex.
path.valuePath value, default /.
methodHTTP method.
headers[]name, value and type (exact or regex).
query[]name, value and type (exact or regex).

Regular expressions must match the whole value. Dot segments (., .., also percent encoded) are removed from the path before matching, so /public/../admin is routed and forwarded as /admin.

When several rules match, the most specific wins, in this order: higher priority, exact path, longest prefix, method match, more header matches, more query matches, then rule order. Requests that match no rule get 404.

Rule ​

FieldDescription
filters[]Run in order before the middlewares.
middlewaresNamed middlewares, usually a service.
backends[]Weighted middleware chains; one is picked per request. weight: 0 disables a backend. status answers with a fixed status instead.
timeoutRequest timeout, including all retries. When it expires before a response starts, the response is 504.
retrySend the request again when the middlewares and backends answer a retryable status. See below.
backend_timeoutWith retry, bounds each attempt. A timed out attempt answers 504, which can be retried.
statusStatus when the chain does not answer, default 500.

Retry ​

FieldDefaultDescription
codes[502, 503, 504]Retried response status codes. An unreachable upstream answers 502.
attempts1Retries after the first request; 0 disables retries.
backoff0Minimum wait between attempts.
max_body_size1MiBRequest bodies up to this size are buffered and sent again. Larger requests are sent once without retries.

Filters run once per request; middlewares and backends run again for each attempt, so a retry can pick another backend. A retryable response is discarded before anything is sent to the client, and the last attempt's response is returned when all attempts fail. A service that cannot reach any upstream and an attempt exceeding backend_timeout are retried even when their status is not in codes.

Filters ​

FilterDescription
request_headersset, add and remove request headers.
response_headersset, add and remove response headers.
rewritehostname and path (replace_full_path or replace_prefix_match).
redirectscheme, hostname, port, path and status_code (default 302).
mirrorSame options as the service mirror.
corsallow_origins, allow_methods, allow_headers, expose_headers, allow_credentials and max_age (default 5). Preflight requests are answered by the filter. An origin * allows every origin, * in an origin host matches any number of labels to its left (https://*.example.com). Wildcard methods and headers are answered with the requested values. Allowed origins are echoed in Access-Control-Allow-Origin.
middlewaresRun named middlewares at this position.

gRPC ​

Rules in grpc match requests with content type application/grpc instead of rules. A grpc match selects the service and method, and can be combined with headers:

yaml
routes:
  gateway:
    grpc:
      - matches:
          - grpc: { service: pkg.Users, method: Get }
            headers:
              - { name: version, value: two }
        middlewares: [users_v2]
      - matches:
          - grpc: { service: pkg.Users }
        middlewares: [users]

grpc.type is exact (default) or regex. More specific matches win: longer service, longer method, more headers. Errors of the gateway are returned to gRPC clients as gRPC status codes (Unimplemented when nothing matches, Unavailable when the upstream is unreachable). Use a service with h2c: true for plain text gRPC upstreams.

Set passthrough: true to call the next middleware of the router after a rule's chain, or when no rule matches, instead of answering.

listeners lists the hostnames of the TLS listeners sharing the entrypoint ("" for a listener without hostname). A TLS request whose Host header selects another listener than its TLS server name, for example on a reused HTTP/2 connection, is answered 421 Misdirected Request. Listeners are selected by exact hostname, then the longest wildcard, then the listener without hostname.
